# cunho design, layer 1 (on paper)

This is the issuer described in plain English before any code exists. Every statement here traces back to a row in `binder/`. Code comes next, in Python, and must match this document.

## 1. What cunho is

cunho is the credential issuer role of the EU Digital Identity Wallet, as Regulation 910/2014 (amended by 2024/1183), its implementing acts and the ARF define it, written as software anyone can run.

It is generic. It does not know who runs it. A PID provider, a bank issuing qualified attestations, a university or a municipality all run the same code with a different profile and configuration. The only part each operator writes is one small plug that answers: where does the data about this person come from?

## 2. The problem it answers

The public issuers we tested are built on the rules, but the rules reach developers as a list of sentences. The list does not say clearly which sentences are hard requirements, which only apply when a feature is offered, which are recommendations, which bind the operator instead of the software, or where in a program each one belongs. So rules end up in the wrong place, or nowhere.

cunho gives every rule three things: its strength, checked against the original text (`binder/BINDER-STRENGTH.csv`); the component that enforces it (`binder/BINDER-PLACEMENT.csv`); and a test that proves it.

## 3. How a rule becomes code

1. Each binder row has a rule id, for example `DPOP.JTI_REPLAY`, and a component.
2. The component has one named check function per rule id. The function's docstring quotes the source and the strength.
3. When a check fails, it raises one error type that carries the rule id. A single mapping turns it into the exact HTTP status and OAuth or OpenID4VCI error code the spec requires. What a client sends is refused where it is parsed, so it cannot raise anything deeper down: numbers are bounded before any arithmetic (a JSON integer of more than 20 digits is refused when it is parsed, and a NumericDate must lie within 2^53 seconds of zero); a JSON string must be Unicode text, so the escape of a lone UTF-16 surrogate is refused in every document, member names included; and every certificate in a key attestation is read in full when it is loaded, while anything the certificate library raises later in the path checks, for an anchor or a CRL too, is a refusal. The tests and the stress harness fuzz correctly signed DPoP proofs, key proofs and key attestations, with text that includes lone surrogates and certificates changed byte by byte, so the checks after the signature are reached too. Earlier reviews each found an input that reached a 500 before these rules, and the later ones found none; that no client input produces one now is what the fuzzing shows, not a proof. JSON is read only as UTF-8 (RFC 8259 §8.1). A 500 is left for cunho's own failures, such as an audit log it cannot write, and says so. Error descriptions sent to wallets are fixed text that never echoes what the wallet sent; errors on operator requests may name the operator's own offending field or configuration id. All of them are limited to the characters RFC 6750 allows, so no input can make a response header unencodable.
4. A registry, generated from the binder, lists every rule and the milestone that implements it. Build-time tests fail if:
   - a rule of the current milestone has no code;
   - a rule the code refuses on has no test that triggers the refusal (`covers`); every refusal reports its rule id as it is raised, and a `covers` test fails unless the rules it names actually refused something while it ran;
   - a rule that is an obligation, something cunho must produce or do, has no test that checks the behaviour itself (`obligation`); a decorator alone does not count, and an `obligation` test fails unless code that claims the rule ran while it did;
   - code or tests cite a rule that is not in the binder.

   A mutation run (`tools/mutation/mutate.py`, its own CI jobs) then switches off each rule; removes each refusing statement and each `raise` in the engine, whatever it raises; and alters each condition that guards a refusal (negated, each `and`/`or` operand dropped, each `not` removed, each comparison moved across its boundary), plus hand-written semantic mutants such as a replay cache that lives one second. Each change must make at least one test fail. Mutants that cannot change behaviour are listed with a reason in `tools/mutation/equivalent.py`. Negative tests assert the rule and the reason of the refusal they expect, so a case refused by some earlier, unrelated check does not count.
5. Operator rows do not become code. They become operator documents (`docs/operator/`) and, where possible, configuration that refuses to start when a required item is missing.
6. Rows that bind someone else (wallets, member states, rulebook authors) are kept as context. The software reads their output but owes nothing.

Strength decides behaviour:
- MUST on software: always enforced.
- Conditional MUST: enforced whenever the feature it depends on is switched on, for example deferred issuance.
- SHOULD: implemented and on by default; switching it off is logged at startup.
- MAY: offered as an option.

## 4. Components

Rows per component, from `binder/BINDER-PLACEMENT.csv`:

| status | 53 | Status lists and revocation, including revoking PIDs when the wallet or key behind them is revoked |
| metadata | 34 | Issuer and authorization-server metadata, signed metadata, reuse policy, registration certificate |
| oauth | 46 | Offers, pre-authorized code and tx_code, authorization code with PAR and PKCE, tokens, DPoP, nonces |

| trust | 34 | Trust anchors from the official lists, certificate path checks, certificate profiles, wallet attestation |

Design decisions per component, each drawn from what the research showed works or fails:

- **oauth.** All 12 DPoP checks from RFC 9449 §4.3, with a replay cache. Nonces are single-use, typed per purpose, and consumed only after the signature checks pass. A wrong tx_code does not burn the offer; after `tx_code_max_attempts` wrong codes the offer is cancelled, as every other offer that ends before its time: in one transaction with its entry in the audit log (`offer.cancelled`, cause `tx_code_attempts`), with a line in the security log, and with the person's data leaving the vault. That transaction takes the offer as a request with the right code does, so when the right code came in first the offer is redeemed and nothing is ended or erased. The count of wrong codes lives as long as the offer itself, by the expiry under the offer's MAC, whatever `offer_ttl` is set to later. Stored tx_codes are keyed hashes. An access token yields one credential request per configuration, and no key is bound twice for one subject: a key stays claimed until no token of its offer or login can be shown any more, across every access token a refresh gives, by the ends the refresh token and the access tokens carry under their MACs and not by the lifetimes as they are set that day, and what cunho keeps of it is a keyed reference, never the key; a configuration and its keys are claimed together, and a request refused or failed before its issuance commits gives them back, so the wallet can ask again and the offer is never called live for something it can no longer issue. A request repeated under the same token for the same configuration, with fresh proofs for the same keys, gets the credentials the first one got (OpenID4VCI 1.0 §8.3; the OIDF suite asks a token more than once); no second credential is made on a key (ARF ISSU_35). That reply is kept sealed under the keyring until the token expires and goes when the subject is closed; an erasure counts it as data held. Pre-authorized codes are single-use, enforced atomically. The authorization code flow (HAIP §4) takes pushed requests only (PAR), PKCE with S256, an exact redirect URI from the operator's allow-list for the attested wallet solution, and wallet attestation as client authentication at PAR and at the token endpoint (HAIP §4.4.1), in the draft-07 shape or the one TS3 v1.5.2 follows. The request URI lives under 600 s, is used only by the client that pushed it, and is spent when a login it started completes (FAPI 2.0 SP §5.3.2.2 note 3: until then a reloaded page is not turned away, up to eight times), a mark kept for the longest a request URI and a login may be set to live, not for the lifetimes as they are set that day; the code lives at most 60 s, is bound to the attested client, its instance key and the DPoP key shown at PAR, and is taken in the transaction that writes the access token, so a second use is refused and revokes the token the first use yielded. The operator's login service reports who logged in to `/admin/logins/{login_state}`, with the same subject data as an offer and `loa=high` for a PID; that report creates the subject as an offer does, and its answer gives the URL to send the person's browser back to, with a completion secret only the login service learns, so the wallet that started the login cannot collect the code itself. Every authorization response carries `iss` and `state`, a cancelled login gives `access_denied`, and every redirect is a 303: the framework's own redirect of a path with a slash too many is switched off, so such a path is not found. A built-in test login, for tests and the OIDF suite, refuses to start in production, and production refuses to start without the login service. The code exchange also gives a refresh token (`refresh_token_ttl`, 30 days by default, at most a year), bound to the attested wallet solution and its instance key, not to a DPoP key (RFC 9449 §5: the attestation sender-constrains it), and not rotated: each use, with the attestation again, gives a new access token, bound to the DPoP key shown then, for what the authorization covered, or a part of it, so a credential is issued again to the same wallet unit (ARF ISSU_63, ISSU_65). While it lives, the subject's data stays in the vault and the subject counts as live; revocation, erasure and cancellation close it as before, and a reused code ends its refresh token too. Closing a subject removes the refresh token's row and the record of the spent code with it, since both name the wallet instance beside the subject. A scope of the authorization that names no configuration any more, after a restart that published it under another scope, is granted nothing at a refresh. The pre-authorized flow gives none. It is anonymous unless the token request carries a wallet attestation: then the client is authenticated with every check the code flow makes, and the token is bound to it, so a key proof may name it in iss and its status period caps validity (OpenID4VCI 1.0 §6.1, App. F.1).
- **proofs.** The full OpenID4VCI App. F.1 and F.4 checks, plus TS3 key attestation. The credential is bound only to a key the wallet proved it holds. Each key in a batch gets at most one credential. An attestation's signature is checked under its own certificate before that certificate's path is: checking the path asks for the chain's revocation, which may fetch, and a wallet provider's chain is public, so in the other order anyone could have cunho fetch for a chain they signed nothing under. The same order holds for wallet attestations and for wallet providers' lists. Every key attestation of a PID request must state its status period: one that states it does not stand in for another of the same request that does not.
- **issuance.** Every rejection returns a typed error, never a 500. `batch_size` is published once, from one setting. Requests above it are answered with a clear error. The spec would also allow issuing fewer, but silent truncation is what we saw go wrong. JSON that cunho is sent may nest 64 levels deep and no deeper, a base64url value, a date or a picture is matched whole (a final line feed is not passed over), and a query that is not UTF-8 is refused by the route, not by the framework before it.
- **credentials.** Rulebooks are configuration, not code. The EC's 31 credential configurations load unchanged. Protocol claims (iss, cnf, vct, exp, status) are written last, so data from the plug cannot override them. Timestamps are rounded so a batch cannot be linked. Expiry is capped at the key attestation's status expiry (ARF ISSU_12c), in the code flow at the wallet attestation's too, and at the end of the document itself, whichever of `date_of_expiry` and `expiry_date` its rulebook calls it. Subject data with a member named `_sd` or `...`, at any depth, is refused at the offer: RFC 9901 keeps both names, and a credential with a disclosure under one of them is rejected by every verifier. Each SD-JWT VC follows ETSI TS 119 472-1 clause 5, which CIR 2024/2979 Annex II makes binding: `vct` with the `vct#integrity` of the Type Metadata document the operator supplies for it (production refuses to start without one for each published type), `nbf` and `exp`, a `category` only from a qualified or public-body attestation provider, `cnf` with the holder's public key only, the Token Status List reference, `_sd_alg`, and no audience or renewal component; qualified and public-body providers, like PID providers, name their signer's certificate by `x5u` and `x5t#S256`. An mdoc (M4) is an IssuerSigned structure whose Mobile Security Object the document signer signs: a separate key whose certificate carries the purpose id-mdl-kp-mdlDS under an IACA, sent in x5chain without the IACA, with x5u and x5t in the protected header for PID, QEAA and PuB-EAA providers. Subject data for an mdoc is an object of namespaces of data elements, as the configuration's claim paths name them; each element gets its own random salt and a digest id drawn at random, CBOR is written in the deterministic encoding of RFC 8949 §4.2.1, dates are whole seconds in UTC, and the MSO carries the holder's device key and the Token Status List reference. An mdoc starts at the coarse time, or at the start of its document signer certificate when that came later, since a reader checks that the MSO was signed while the certificate was valid (ISO/IEC 18013-5 §9.3.1). The same status list is served as a CWT when a client asks for `application/statuslist+cwt`. The MSO's status_list also names the certificate that issued the status list's signing chain, the relying party's trust anchor for that list, since the list is not signed under the IACA (CIR 2024/2979 Annex II EAA-6.2.10.1-06, -13.1). Without a document signer no mdoc configuration is published. The PID comes from the operator once, in the SD-JWT VC claim names, and is issued in both formats (ARF PID_02): for the mdoc, cunho maps each claim to its data element of the PID Rulebook's §3.1 table in the namespace eu.europa.ec.eudi.pid.1, dates as full-date (tag 1004), the portrait as the bytes of its JPEG; every text is valid Unicode of at most 150 characters, and a claim the mdoc configuration lists no element for is refused. The PID carries only what the Annex of CIR 2024/2977 (as replaced by 2026/1731) defines: anything else belongs in a domestic namespace or type (Annex §4.1, §4.2), so `trust_anchor`, `attestation_legal_category` and `address.house_number`, which the PID Rulebook still lists, are refused in either format, the house number belonging in `street_address` as the Annex's resident_street includes it. A claim a configuration lists outside the Annex (the reference configurations' trust_anchor, house_number and resident_house_number) is neither published nor issued, with a warning, and a domestic namespace is not issued yet. A PID provider that publishes both formats offers the PID in both, and production refuses to start one that publishes only one. The rest of clause 6 holds too: every mdoc attestation that is not the PID or an mDL gets the issuing authority's name from the document signer's certificate, an identity code of its own and its issue date in the ISO/IEC 23220-2 namespace, a qualified or public-body one its category, and the MSO's protected header carries the signing time and the certificate's x5t (CB-AdES); x5chain stays a bare unprotected header, where ISO/IEC 18013-5 puts it and mdoc readers look, though CB-AdES asks for it in uHeaders, the one point of clause 6 left open. A configuration is a PID when its `vct` starts with `urn:eudi:pid:`, which also covers national PID types; a PID configuration, and every configuration a PID provider publishes, must require key binding with a key attestation that states `key_storage`, or cunho does not start.
- **status.** Token Status List with random indexes reserved atomically, decoy entries at creation and new decoys over time, short `exp` and `ttl`, a separate signing key, and lists published on fixed moments. Each offer gets its own subject reference, so revoking a subject reference flips every credential issued from that offer; an operator who gives a person handle when creating offers can revoke every credential of every offer made for that person at once (cunho stores only a keyed reference of the handle, never in the log, for as long as a credential from the offer can be valid; an operator who gives none maps persons to subject references themselves). Each revoked bit is set at once but shows in the published list at its own random moment within `status_revocation_jitter` of the time the revocation was made (an hour by default; the jitter, a margin of two minutes, the publication interval and the token `ttl` together stay within 24 hours). The moment and the publications go by the same time, the clock watch's (see time), so a wall clock that reads ahead or behind, whether it stays so or is put right later, moves neither: a revocation shows within its jitter and a publication interval of when it was made, in time that really passed, and nothing shows before its moment. When the watch cannot vouch for the time, after a host restart until it is trusted, the bit shows at the next publication, without its jitter, and a warning says so: a later moment would be a guess; meanwhile a list shows what it showed and those bits, and nothing scheduled comes due. When a host restart lays the base behind the time before it, because that time read ahead, a queued moment later than any a clock reading right lays (two maintenance intervals and the jitter ahead, decoys included) is laid again within the jitter, so such a time hides a bit for that long at most. A list is published every `status_publish_interval` seconds (a minute by default): the token's `iat` is that moment and it shows the bits due by then, so neither the token nor its `iat` changes at the moment of a revocation; with a jitter of 0 a revocation shows at the next publication, and its moment, to within the interval, with it. The published bits are kept in the store and brought forward from a queue keyed by the moment each bit shows, so a publication costs the bits that came due and a poll between publications is answered from the worker's memory, however many bits are hidden; each worker signs a list once per publication, and the background task brings every list forward about once a minute, and a poll brings its list forward whenever it comes, both by the same time, so neither can show a bit early. `/status` is rate-limited per client like the other public routes, with its own budget. A list keeps the size it was opened with, so changing `status_list_size` applies to new lists only. A list whose stored size or published bits are missing, or do not fit each other, is not served at all (a 500 and an error in `cunho.security`): an answer of zeros would take back every bit it ever showed. Revoking a subject also closes its offer, whatever its data in the vault, and erases that data (erasing a subject closes it the same way): the pre-authorized code and any access token obtained with it give nothing more, and a configuration still being issued is refused in the transaction of its own log entry. An operator can cancel an offer on its own (`POST /admin/offers/{subject_ref}/cancel`), which is logged and erases the subject data it held. New decoys arrive as clusters at Poisson moments: a cluster's size is drawn from the sizes of the batches cunho actually issued, and each of its bits shows at its own random moment within the same window. Every list has its own schedule, laid down when the list opens. So k new bits appearing within one window may be a decoy cluster or a revocation, in the ratio of the decoy rate (`status_decoy_churn_per_day`) to the revocation rate, and neither their timing nor their number tells them apart. Decoys do not hide the overall trend in the count, and they hide little when revocations far outnumber them; an operator sets the rate (`CUNHO_STATUS_DECOY_CHURN_PER_DAY`) with that in mind. Every setting this document leaves to the operator can be set from the environment. The cluster sizes follow the sizes of issuance requests, while a revocation covers every live credential of a subject reference or of a person handle, which can span several requests; the two match as long as the credentials revoked together come from one request, as with batch issuance. Revocation reports only real, live credentials. Revocation chaining (below) reads the wallet and key attestation status of every live PID again at least every `chain_interval` (six hours by default, at most a day), and revokes PIDs whose wallet was revoked (CIR 2024/2979 Annex Ib LC_GEN-4). At issuance cunho checks the wallet attestation's and the key attestation's entries on their wallet provider's status lists (see trust); the re-check every 24 hours is the M4 job above.
- **trust.** Fails closed. With no trust anchors loaded, nothing is trusted. Certificate paths are checked against RFC 5280 §6.1: validity, CA flags, keyCertSign, pathLenConstraint, no unknown critical extensions, no name constraints (refused, since they are not processed), and revocation (§6.1.3(a)(3)): every certificate below the anchor must be shown not revoked, or the path is refused. A certificate that names a CRL distribution point is judged by that CRL, fetched and kept until its nextUpdate; one that names only an OCSP responder by an OCSP response checked in full (RFC 6960 §3.2 and §4.2.2.2: the responder is the issuer or a delegate it named for OCSP signing, the nonce when one was sent, thisUpdate and nextUpdate around now); one that names neither by the operator's file `wallet_provider_crls`, whose CRLs are also pooled with fetched ones. A CRL must be current, correctly signed by the certificate's issuer and complete, and the certificate not listed in it. Whatever cannot be fetched, read or checked leaves the status unknown, and the path is refused. When the file holds several current CRLs from one issuer, the newest (by CRL number, then by thisUpdate) decides, and an older one cannot take a revocation back: only a certificateHold that the newest CRL no longer lists is let go. The newest CRL seen at a distribution point is remembered, so an older one replayed by the network cannot undo a revocation either. That memory is each worker's own and is lost on a restart, unlike the status list watermark below, which the store keeps: a worker that has never seen the newer CRL can be shown an older one that is still in force, until its nextUpdate. cunho reads the file again whenever it changes. A development run without the Commission's list checks the file alone, and without the file logs that revocation is not checked. The key attestation signer must be an end entity for digital signatures: not a CA, no `anyExtendedKeyUsage`, and no TLS, code signing, e-mail, time-stamping or OCSP purpose in its extended key usage. An intermediate whose extended key usage names only such purposes cannot vouch for one. When the deployment sets `ka_signer_policy_oids` (production must), one of those certificate policies must hold along the whole path: every intermediate asserts it, or anyPolicy where anyPolicy is not inhibited, and the signer asserts it itself (anyPolicy is not accepted below a certificate with inhibitAnyPolicy, from that certificate on, and policy mappings are refused because they are not processed). Without mappings this is the valid policy tree of RFC 5280 §6.1, kept simple: each certificate only narrows the policies the path is valid for, and the path is refused when none is left, so an intermediate for one policy cannot vouch for a signer of another. inhibitAnyPolicy and policyConstraints may be marked critical, as RFC 5280 asks of CAs; a policyConstraints that requires an explicit policy is honoured when the deployment names its policies and refused when it does not. When several anchors hold the key that signed the top of a chain (an expired root next to its renewed copy during a rollover), each is tried. Every certificate in the path, the anchor included, must use an agreed key (P-256, P-384, P-521 or Brainpool curves, or RSA of at least 3072 bits) and a signature with SHA-256, SHA-384, SHA-512 or one of their SHA-3 counterparts: a list of what is accepted, which CRLs and OCSP responses are held to as well. The anchors come from the Commission's list of wallet providers (ETSI TS 119 602 Annex E), which production requires: a file an operator job keeps current, read again whenever it changes, and accepted only when its compact JAdES signature verifies under the signer certificate the operator pinned from the Official Journal, whose country and organisation must be the list's territory and scheme operator, when it is the wallet providers list type for the EU, its next update is ahead and at most six months after its issue, and its sequence number is not lower than the highest seen, which the store keeps. Each wallet solution's issuance service gives the anchors of wallet and key attestation signers, and its revocation service those of its status list signers; a service of any other type, or one with a ServiceStatus, which the profile forbids, gives none. A list that cannot be used stops the start, and once running leaves no anchors until a good one is in place. A development run without the list reads anchors from PEM files (`wallet_provider_anchors`, `wallet_status_anchors`). Both certificate styles are supported: `x5c` (HAIP 6.1.1) and `x5u` with `x5t#S256` (the 2026/1731 PID annex). A deployment declares which profile it uses. A wallet attestation, at PAR and at every token request, and a key attestation, at the credential request, are accepted only when their entry on their wallet provider's Token Status List says VALID (ARF WUA_25, TS3 v1.5.2 §2.4.3): the list is fetched from the URI the attestation names, through the fetcher that sends only to the operator's `fetch_hosts` and to public addresses, with a two-second budget. A URL whose fetch failed is not tried again for five seconds, so the requests that waited for that fetch share its failure instead of each making it again in turn. A host is sent at most 60 requests a minute; a request that finds no place left is refused, which is not remembered as a failure of the host, and revocation chaining, which can wait, waits for its place. It must be a `statuslist+jwt` signed under an `x5c` chain to the anchors for status list signers, the signer's revocation checked as for the attestations; its `sub` must be that URI, its `iat` not ahead, its `exp` present and ahead; `bits` 1, 2, 4 or 8, and `lst` a zlib stream inflated no further than 16 MiB. A list older, by `iat`, than one already seen at the same URI is refused, so a replayed list cannot bring back a revoked attestation. A list is kept until its `exp`, its `ttl` or an hour, whichever is first. Anything that cannot be fetched, read or trusted refuses, as a revoked entry does: invalid_client at the authorization server, invalid_proof at the credential endpoint. The status reference is used for the check and never kept (C_KA-1). Production refuses to start without the Commission's list and `fetch_hosts`; a development run without either the list or `wallet_status_anchors` logs that status is not checked.
- **metadata.** Everything advertised is contract-tested against the real routes. The issuer metadata is JSON by default; a client that prefers `application/jwt` (Accept, the higher weight winning and JSON winning a tie) gets the same document as a JWT of type `openidvci-issuer-metadata+jwt` with `sub` the issuer identifier, `iat` and an `exp` `signed_metadata_ttl` later (a day by default, at most a week), signed with the issuer's access certificate and its path up to but excluding the anchor in `x5c` (OpenID4VCI §12.2.3, HAIP §4.1, ETSI TS 119 472-3 §4.2.1, §4.2.2). It is signed again each minute of issuer time. The access certificate is checked at start: not self-signed, its `x5c` leaving out the anchor, and its key neither the credential nor the status list signing key; production refuses to start without it. The document carries `issuer_info` with the registration certificate by value and the registrar dataset (§4.2.3; production refuses to start without them, owner decision 7), and `preferred_client_status_period` when set (TS3 v1.5.2 §2.4: a preference the wallet meets, not a refusal; the credential's validity already ends before `client_status.exp`). Each configuration's reuse policy is the ARF one (`arf_annex_ii`) in the encoding of §4.2.4: each option names method A (`once_only`) or B (`limited_time`, also spelled `limited-time` in the same clause), and may add C (`rotating-batch`) and per relying party; A, C and per relying party give a `batch_size` of 2 or more, A a `reissue_trigger_unused` below it, B and C a `reissue_trigger_lifetime_left`. No embedded disclosure policy is published: §4.2.5 gives its data model and no metadata member for it, so the rule is marked partial until one is named. The authorization server metadata advertises the code flow (PAR required, S256, `attest_jwt_client_auth`, `iss` in responses) beside the anonymous pre-authorized grant.
- **signer.** No private key ever leaves the signer interface. A key setting names a PEM file, a key in an HSM by a `pkcs11:` URI (RFC 7512, through python-pkcs11, tested against SoftHSM2), or a key in AWS KMS by `aws-kms:` and its id, ARN or alias. The file signer exists for development only: production refuses a file for every signing key. The HSM and KMS signers hash the input themselves and have the device sign the digest, check each signature against the certificate's key before using it, and sign once at the start, so a key that is not the certificate's stops the start. KMS is pinned to the key's ARN at the start; an HSM session dropped by the token is opened again once before a signature fails. The credential signer's certificate must name the issuer in its subjectAltName, or cunho refuses to start. The chain file must be in order, leaf first; `x5c` stops before the first certificate that is one of `signing_trust_anchors` (same subject and key, so a cross-signed copy counts), and without that setting before any self-signed certificate. Production requires the setting. When `signer_certificate_url` points at cunho itself it must be `/certs/signer.pem`, where cunho serves the chain whose leaf `x5t#S256` names; a URL elsewhere is the operator's to host.
- **keyring.** One master secret, in a file kept apart from the database and its backups, yields the vault key-encryption key, the audit MAC keys, the DPoP nonce key, the tx_code hashing key, the MAC key of offer and access-token rows, and the P-256 key that signs the audit head statement (used for nothing else; the internet-facing status-list key is not reused). Production refuses to start without it.
- **audit.** See section 7.
- **store.** Memory for tests, SQLite for one host, PostgreSQL for several; each undoes every write of a transaction that fails part-way, and one contract test holds all three to the same behaviour. In PostgreSQL every write transaction first takes one advisory lock (`pg_advisory_xact_lock`), so writers go one at a time across every worker and host as they do on one SQLite file, and keys are kept as UTF-8 bytes so they sort as SQLite's do. Several uvicorn workers may share one SQLite file: every single-use operation and every read-check-write sequence (audit head, status bit, list opening, decoy schedule) runs in one `BEGIN IMMEDIATE` transaction, and writers wait up to 30 seconds for the lock before the request fails closed. Several workers are correct but not faster on SQLite, which takes one writer at a time: in the stress run (`evidence/stress/`) four workers issued fewer credentials per second than one. Prefix lookups are key ranges, compared byte for byte. Reads never return an expired entry; expired rows are deleted by the background task about once a minute, in batches of 1,000 rows, never by a request. Expiries are stamped and read by the clock watch's time (see time), so a wall clock that is stepped neither ages a replay entry nor revives a closed offer. No route calls the store on the event loop: a call waiting for another worker's lock would stall every request of the worker. Reading the time is a store call, since the clock watch reads its base from the store, so the status route, cached token included, and the count of refused admin requests run in the thread pool too (second reviewer, CX-14). Offer and access-token rows carry a keyring MAC over their key and content, with their own expiry inside it, and are ignored when it does not verify, so whoever can write the database cannot point a token at another person's data; the vault ciphertext is bound to its subject and to the offer it was created for. Other operational rows (status bits, issued-credential records, nonces) are not MACed: a database writer can change a status bit, which the audit log, with its keyed status references for every revocation, lets an operator detect but cunho does not check by itself. The status-token cache and the rate limiter live in each worker's memory. The limiter keeps one table per route group (token, nonce, credential, admin and status), counts IPv6 clients per /64, and when a table is full it drops the client seen least recently instead of refusing newcomers.
- **schema.** The store carries a schema version. A new store gets it on its first start; a store with a version cunho does not know refuses to start. A store written before the version existed (by `45ec9be` or `382505f`, the code the fifth and sixth reviews read) is upgraded once, in one transaction, before anything else runs: each list gets the size it was opened with (the earlier code had none and took the setting, so the upgrade takes the setting too, and refuses to start when a slot lies beyond it), the bits still hidden are queued by their moments, the published bits are rebuilt from the slots (every revoked slot, decoys included, except those still hidden), the subject references the store still names are recorded as handed out, since the earlier ones carry no keyed tag, and an offer whose data is still in the vault counts as live, for every configuration the deployment issues, until its window ends. The upgrade runs in an audit transaction with a `store.upgraded` entry, so it stands or falls with its record. A store without a version is also what a database writer leaves who removes the version row, so production upgrades only when told to (`store_upgrade`, `CUNHO_STORE_UPGRADE=true` once), as it starts a new anchor only when told to. What the upgrade does not do: in an anchor file where `45ec9be` repaired a torn line, the fragment it left before the whole line is bytes no line declares, and fails verification until an operator cuts the fragment out.
- **maintenance.** A background task in each worker, never a request, sweeps expired state, repairs a damaged audit anchor and brings status lists forward about once a minute, and every `maintenance_interval` (an hour by default) prunes the audit log (never past the last anchored entry), schedules decoys, logs the count of failed operator logins and checkpoints the SQLite write-ahead log. Each step works in short bounded transactions, so several workers can run it at once.
- **time.** Everything cunho decides by time goes by one time, the clock watch's: the store's expiries, the lifetimes of offers, tokens, nonces and proofs, a credential's validity, the moments of revocations, the publication of status lists, the audit entry times, sweeping, decoys and pruning. That time is a base, a wall-clock reading the watch trusted, moved on by the host's own clock, which counts the time that really passed, sleep included, and which wall-clock steps do not move. There is one base per boot, kept in the store, so every worker on the host, and a worker started again, reads the same time, and it never goes back. Every worker reads the base row at every reading of the time, inside the store transaction when there is one, and checks its MAC again only when the row changed, so a base laid again by a forced run in one worker is every worker's time at once, and none stamps or reads an expiry by the time it had before (second reviewer, CX-13). A sweep reads the time again inside each of its transactions and deletes by the earlier of that and the time it was started with, so a correction made meanwhile deletes nothing stamped by the corrected time (second reviewer, CX-15). Pruning does the same in each of its batches, with its cutoff moved back as far as the time went back, and stops once the watch says it has not settled, as it does for an interval after a forced run in any worker (second reviewer, CX-16). Status publication lays again moments queued later than a clock that reads right could lay, by the time read inside that transaction too, so a forced run that moves the time forward meanwhile cannot make a moment rightly laid by the new time look too late and bring its bit forward (second reviewer, CX-21). The bits that come due are brought forward by the earlier of the publication's cutoff and the one read again inside that transaction, so a correction back meanwhile cannot show a bit not yet due (second reviewer, CX-23). Decoys are scheduled by the time read inside the transaction that lays them, and a SQLite row that expires is written in a transaction with its expiry stamped inside it, so neither goes by a base another worker replaced while this one waited for the write lock (second reviewer, CX-24 and CX-25). The same holds for the expiry under an access token's MAC, a c_nonce's time and a revocation's moment: every read of the time whose value is written to the store, or is the cutoff of something that cannot be undone, is made inside the transaction that writes it (CX-29). The watch reads the wall clock and the host clock together, before it waits for its lock or the store, so a pause before the base is laid cannot leave the time behind for the boot; and it reads, chooses and lays the base in one store transaction, so workers starting together on a new boot lay one base between them and none replaces a base another already goes by (second reviewer, CX-5 and CX-6). The base and the latest time seen are kept under a MAC from the keyring, so whoever can write the database alone cannot move the time that every expiry goes by: a base that does not verify is taken for none, with an alert, as after a host restart (second reviewer, CX-11). After a host restart a latest time seen that does not verify, or none, means the slow way, a wait of an interval, so deleting it cannot take the time back to the base; a writer who kept an older row can put it back, which takes the time back to that older reading and never behind the base. A MAC alone does not stop an older base, kept from before a forced run, from being put back on the same boot: it verifies, and it would take the time back by as much as the operator put it right. So a forced run lays its base and logs a `clock.trusted` entry in one audit transaction, and that entry's anchor line names the base (boot, host-clock reading and time), on the append-only file outside the database. Every worker keeps the newest base it knows of on the boot, from the bases it went by and from the anchor, and refuses a base laid before it, at an earlier host-clock reading. It asks the anchor at every reading of the time, through a reader that takes no lock and keeps its own place in the file, apart from the writer's, so a base put back is refused at once in every worker, also one that has not ticked since; a line complete apart from its newline counts, as the next write closes it (second reviewer, CX-18 and CX-19). A line that cannot be parsed or MACed is no line to that reader, and a reader that fails keeps the newest base it found, so a malformed line cannot stop the time (second reviewer, CX-22). A refused base is taken for none, with an alert, as one that does not verify (second reviewer, CX-17). When the transaction a base is laid in fails, in its body or at its COMMIT, the worker's memory of the clock goes back with the store, inside the rollback and before the store's lock is released (`Store.on_rollback`), so no request sees the base the store went back to beside a floor that names the one undone (second reviewer, CX-20 and CX-30). A base laid by the watch itself, on the first start of a store or after a host restart, is not anchored: it is the first of its boot, so nothing on the boot came before it. It is laid on the first start of a store, and after a host restart at once when the kernel reports its clock synchronised by NTP and the reading is not behind the latest time the watch saw, otherwise once the wall clock has kept pace with the host clock for a whole interval and the kernel does not say it is unsynchronised. Until then the watch cannot vouch for the time: requests go by the wall clock, revocations show at the next publication, and sweeping, decoys and pruning wait. On the same boot the wall clock is then only compared with the time: a reading more than two minutes off is logged as an error every minute, and nothing follows it, so a clock stepped once, or a little at every reading, moves nothing (review 7, M1 and M2). An audit entry carries the time, and keeps the wall-clock reading as `clock` when it read more than two minutes off. Pruning, which cannot be undone, waits for more: an interval after the base was laid, and while the wall clock reads behind the time, which may mean the base was laid from a clock that read ahead and was put right since; a wall clock ahead of the time can only mean the time is behind, which prunes less. A forced run (for tests and the operator's own scripts) lays the base again from the wall clock. What this gives up: on one boot cunho does not follow a correction of the clock it laid its base from. A host started with a wrong clock, when the base was laid from it all the same (the kernel reported sync, or the wrong time kept pace with the host clock for an interval), keeps the wrong time until the host restarts or an operator runs a forced maintenance, while an error says every minute that the wall clock reads off. A virtual machine whose clocks stop while it is paused comes back with a time behind by the pause, reported the same way. A host clock that NTP does not steer drifts from the wall clock by its own error, seconds a day, until the difference passes two minutes; on Linux NTP steers CLOCK_BOOTTIME with the wall clock. What cannot be told apart remains: after a host restart, a clock that is wrong from the start while the kernel reports sync is taken as right, so NTP must be in sync before cunho starts, and an authenticated time source (NTS, as chrony offers it) is what makes that sync mean something. A clock passed in for tests has no host clock behind it, and is the time as it reads, so a step of it is taken for time that passed; production refuses to start on a host whose boot cannot be named, where the host clock could not be compared across restarts, and a development run there goes by the wall clock alone, with an error.

## 5. Issuer profiles

One setting picks the issuer type. Each type switches on exactly the rows whose `issuer_types` include it:
- **PID provider:** the PID data model, both formats as the PID annex requires (SD-JWT VC in M2; mdoc in M4), revocation chaining (M4), no issuance-log duty beyond the status references.
- **Revocation chaining (M4).** Each credential that lives more than a day keeps, in the store and never in the logs, the status references of the wallet attestations and key attestations it was issued against (both, in the code flow, the one at PAR and the one at the token request; the one shown at a refresh for what that refresh yields). At least every day a background job reads each wallet provider list once, status lists and identifier lists alike (CIR 2024/2979 Annex II EAA-6.2.10.1-16), and revokes every credential whose wallet unit or key storage is revoked (LC_GEN-4, CIR 2024/2977 Art. 5(4)(b)), each revocation logged in its own transaction. A list that cannot be read revokes nothing by default: cunho alerts and tries again, since a revocation cannot be undone and the credential ends by the attestations' status periods anyway (LC_GEN-3); an operator can choose to revoke after some days unchecked. Suspension is not offered: the law allows only valid and invalid. A revoked subject's references go with its credentials; an erased subject's stay as long as its credentials live, since the law asks for the check while they are valid.
- **QEAA provider:** issuance and lifecycle records (ETSI TS 119 471 via CIR 2025/1569, and 910/2014 Art. 24(2)(h)), plus revocation within 24 hours. Every credential carries Annex V as ETSI TS 119 472-1 profiles it (M4): the provider named by its qualified certificate alone, which cunho checks at start; the category; an identity code of 128 random bits per credential; the scheme by `vct` and Type Metadata, or by docType; `x5u` and `x5t`; the status reference. A configuration that names the provider in claims, or attributes of another subject, is not issued.
- **Public-body EAA provider:** like QEAA for record-keeping (CIR 2025/1569).
- **Non-qualified EAA provider:** records of onboarding and key changes only (CIR 2025/2160 Art. 4(3)(b)).

## 6. The flows, in plain English

- **Pre-authorized** (first milestone): the operator creates an offer for a person and gets a QR code, optionally with a PIN. The wallet scans it, trades the code for a DPoP-bound token, asks for a nonce, proves its key, and receives the credential.
- **Authorization code** (HAIP, needed for certification): the wallet pushes its request (PAR) with its wallet attestation, the person logs in through the operator's identity check, and the wallet gets a code, then a DPoP-bound token, then the credential.
- **Review before issuance** (M4, OpenID4VCI §9): the operator may hold a login's credentials for review. The wallet's request is checked in full and answered with a transaction id; the operator releases or refuses; the wallet collects with any token of the same login, so a refreshed one serves when the review outlasts the first. The credentials are signed when collected, bound to the keys proven at the request, so cunho still stores no issued credential. Only the code flow can be held: a pre-authorized token cannot outlive a review. A login may have three issuances of one configuration waiting or refused at a time, so a refresh token cannot fill the operator's list, and a released issuance is collected by one request at a time: another that comes while the first is at work is told to ask again and reserves nothing. The wallet's notifications (accepted, failed, deleted) are logged once per event; their free text is never kept.
- **Encryption** (M4, OpenID4VCI §10): the credential and deferred credential requests may come as a JWE to one of cunho's request keys, and ask for the answer as a JWE to the wallet's key; ECDH-ES with A128GCM or A256GCM, written with `cryptography` alone and checked against RFC 7518's known answer. A request for an encrypted answer must itself be encrypted, so nobody can swap the wallet's key in transit. The parameters are checked before anything is claimed or signed, so a wallet that sends bad ones can try again; error answers are never encrypted.
- **Revocation:** the operator, or the 24-hour chaining job (M4), flips the credential's status slot. The event is logged. For PIDs, the person must be told within 24 hours (2977 Art. 5(3)); cunho has no channel to the person, so the binder places this with the operator (`REVOC.USER_NOTICE_24H`).

## 7. Audit log

Built from `research/LAW-AUDIT-LOG.md`.
- **What goes in:** events only (offer created, credential held for review, released or refused, issued, revoked, status checked by the chaining job, the wallet's notifications), with the operator identity, time, credential type, keyed references to status list slots, a pseudonymous subject reference, and a keyed reference to the grant, which ties each issuance to the offer it came from.
- **What never goes in:** names or other personal data, how the credential is used, who fetched a status list (910/2014 Art. 5a(16), CIR 2025/1569 Art. 4(4)). Not even a credential's exact expiry, which near the end of a document's life is the document's own expiry date: `credential.issued` records the configured validity period instead. The same holds for the web server's own log: the documented uvicorn command lines turn its access log off.
- **Integrity:** each entry carries a MAC over its content and the previous entry's MAC, keyed with the keyring, so whoever can write the database cannot rewrite or reorder entries without verification failing. Inside the database alone, removing the newest entries cannot be detected: an old head can always be put back. So every entry is also appended, MACed under its own key purpose, to an anchor file outside the database (`audit_anchor_path`; production refuses to start without it). The file starts with a genesis line written when the log is new, and its lines form their own MAC chain with a sequence that grows by exactly one. The anchor is read only forwards from its first line, and every line must follow the one before it, its `prev` the tag of that line and its sequence one more, so the end of the anchor is the last line of one unbroken chain from the genesis line. A tagged line that does not follow, such as a copy of one of the file's own lines, which anyone who can append to the file can add without the keyring, is refused wherever it stands: verification reports it and cunho logs nothing until an operator removes it. (An earlier reader took the last valid line as the end, so such a copy moved the end back, and verification then called a store whose newest entries were removed valid.) An operator who finds one keeps a copy of the file as evidence, lifts the append-only flag, cuts the file back to the end of the line before the copy and sets the flag again; when verification then reports the store behind the anchor, entries were removed, and the way back is a new deployment, as after a restore. Each worker remembers how far it has read and reads only what was appended since, and reads the file again from its start when it is shorter than that; a worker's first write reads the whole file, a few seconds per million lines. Verification reads the checkpoint, the head and the size of the anchor together, under the locks every writer holds, and checks the anchor's last line against the store exactly as a writer does before it logs, so it fails whenever cunho refuses to log, and whenever an entry is not anchored yet; it then reads the whole file up to that size and compares every line still covered by the store with the entry of the same sequence (when pruning moves past it meanwhile, it goes on from the new checkpoint, which is MACed like an entry), so history that was once anchored cannot be rewritten, even by someone holding the keyring, without contradicting an older line; it also fails when the store is behind the anchor. cunho refuses to log anything on top of a store that fell behind, so the actions that need a log entry stop. The converse does not hold: damage deep in the log that only a full verification reads, such as an old entry changed, fails verification but does not stop logging. A write to the anchor can stop part-way (a full disk, a crash), the repair of such a write can stop part-way too, and after a power loss some file systems leave NUL bytes where the data should be. Whatever follows the last valid line, found under the lock every writer holds, is damage: the next write closes it with a newline, and the first line it writes declares it, by offset, length and SHA-256, under that line's tag. The reader skips bytes only where the next line declares exactly those bytes, so damage of any shape is repaired by the next write that gets through, while bytes no line accounts for, or a declared stretch changed later, fail verification. Verification never reports valid while damage at the end of the file is not closed yet; the next logged action, or the background task within about a minute, closes it. Each repair gets an `audit.anchor_repaired` entry, with the offset and length, in a transaction of its own before the action's, so an action refused inside its transaction cannot take the record with it. The tests cut a write at every byte, cut two writes in a row at every byte of the second and of the first, or at every fourth byte of the first when the second is not the write right after it, and leave NUL and garbage tails. The lines a crash left out of the anchor are written before the next transaction changes anything, and that transaction is refused when they cannot be, so at most one committed action is ever missing from the anchor; an action whose anchor line could not be written after its commit stands, and is answered as done, and verification reports the entry as not anchored yet until the next logged action, or the background task within about a minute, anchors it. A database restored from an older backup looks exactly like one whose newest entries were removed, so cunho stops; M2 has no step that re-bases the anchor on a restored database, because any such step would also let a deletion through. Until one exists, with the anchor signed by a key off the database host (not yet planned for a milestone), keep the database on storage that survives a crash rather than relying on restores; after a restore, the way back is a new deployment with a new anchor, the old database and anchor kept as the record of what came before. A missing or empty anchor is never started again over an existing log: cunho refuses to start, and a running cunho refuses to log, until the file is restored. Production creates the anchor only when told to, on a new deployment (`audit_anchor_init`), so a database wiped together with its anchor does not pass for a new install; a development run creates it for a new database. The operator puts the anchor file on append-only storage (for example `chattr +a` on a local file system); cunho cannot protect the file itself. Object stores cannot hold it directly, because cunho appends and locks with `flock`, but can keep copies. The head pointer, the pruning checkpoint and the anchor lines use different MAC purposes, so none can stand in for another, and the checkpoint binds the time of the last pruned entry: a checkpoint that drops entries younger than the retention period fails verification. A record that cannot be parsed fails verification instead of raising. Pruning removes only entries that verify, in their chain from the checkpoint, and stops at the first one that does not, with an alert (see Retention). `GET /admin/audit/head` returns a statement of the newest entry, signed with a key used only for that, for the operator to pull and keep elsewhere, and `POST /admin/audit/verify` checks the log against such a statement. Anchor lines are MACed, not signed: signing them with a key that is not on the database host needs the HSM signer of M4. The law asks that records "cannot be easily deleted or destroyed" (ETSI EN 319 401) and names no technique, so this is our choice.
- **Who:** each operator has their own admin token and is recorded by name. A failed admin login never writes an audit entry of its own: it goes to the operational log (`cunho.security`) with a fixed route name and the client's network (IPv4 /24, IPv6 /48), and maintenance writes one aggregate entry per run with counts, fixed route names and times. Revocation reasons come from a closed list, and references must have the form cunho hands out, so no free text enters the log.
- **Erasure:** the personal data behind a pseudonymous reference lives in a separate vault, encrypted with a per-person key that is itself wrapped by the keyring, so the database alone decrypts nothing. Deleting the wrapped key erases the person (GDPR Art. 17) without breaking the chain. SQLite overwrites deleted rows in the database file at once (cunho switches `secure_delete` on whatever the build's default); the write-ahead log keeps old pages until a checkpoint empties it, so erasure is complete after the next checkpoint that no reader holds up. Maintenance checkpoints every interval; when a reader in another worker holds the log, the checkpoint gives up after a second instead of stalling the worker, is tried again about once a minute, and a warning is logged until it succeeds. The key-encryption key does not rotate: a backup taken while an offer was live, together with the master secret, still decrypts that offer's data. The vault entry is erased once every configuration of an offer is claimed, unless a refresh token from the code flow can still have them issued again (then it lives as long as that refresh token), when its subject is revoked or its offer cancelled, and expired entries are swept. An erasure closes the subject as a revocation does, so an issuance that read the data before it is refused in the transaction of its own log entry and hands nothing out. Subject references carry a keyed tag, so an erasure of a reference cunho never handed out is refused, and the `subject.erased` entry says whether there was data left to erase, an expired entry not yet swept included; erasure also removes the link to the operator's person handle, after which that subject's credentials are revoked by its reference.
- **Revocation and erasure are logged first:** the audit entry and the change are written in one transaction, so a revocation never takes effect without its entry. A subject revocation reads the issued-credential records and closes the subject in its transaction, whatever the vault holds, and issuance checks that mark and writes its records in the transaction of its own entry, so a revocation that runs alongside the issuance of any configuration of the offer either finds the new credentials or stops the issuance. A deterministic test pauses the second configuration inside signing, and a slow test races the two configurations against the revocation on three worker processes.
- **Retention:** set by the operator. EU law defers to national law, so cunho refuses to start without a retention value. Entries older than it by the clock watch's time are pruned every maintenance run once the watch has settled (see time), in batches of 500, behind a MACed checkpoint; verification reads the log in pages too. An entry's age is its own time, which its MAC covers, and pruning removes only entries that verify: each one's MAC, the first one following the checkpoint and each later one the entry before it, checked in the transaction that removes them. So whoever can write the database cannot date an entry back, remove entries from the front or put one back from elsewhere and have pruning tidy up after it: pruning stops at the first entry that does not verify, with an alert, and verify goes on reporting it. An earlier rule also went by the newest entry's own time; it is gone, since any anonymous request could undo it and the time no longer follows a clock that jumped.

Each piece was reviewed and mutation-tested as before, and `research/cunho-m4-fixes.md` records each review and what changed. At the end, every M4 rule has code and a test, but one whose condition cunho never meets, which the registry marks not applicable with its reason; the mutation run over every site, condition and hand-written patch of M2 to M4 left no survivor; the slow suites and stress suites 2 and 3 pass on SQLite and on Postgres; the probe passes against a local cunho; the five OIDF plans report only the failures listed with their reasons in `tools/oidf/expected-failures.json`; and the second reviewer found nothing in two looks in a row at the last commit.
- **M5 (done locally):** the public demo, built and checked on one machine. Two engine reads an operator's own pages need: how far a subject has got (`GET /admin/offers/{subject_ref}`: offered, redeemed, issued, closed or expired, each configuration's state and the newest event the wallet reported), and what a pending login is for, with the offer it came from (`GET /admin/logins/{login_state}`), so a login service can ask for consent. A course certificate (`demo/metadata/course`), an SD-JWT VC with its Type Metadata and an mdoc twin, issued by a second cunho as an attestation provider. The demo service (`src/cunho_demo`), an operator's front end that talks to cunho only through the admin API: a page in English and Portuguese where a visitor picks a credential, scans the QR code and follows the issuance step by step, can hold it for review, release or refuse it, and revoke it; the login and consent screens of the authorization code flow; and an operator console behind a password. A container stack (`deploy/`, docs/DEMO.md) with both issuers signing through PKCS#11 in SoftHSM behind Caddy. The probe passes against the course provider as against the PID provider, also through the demo's own login screens; the OIDF HAIP plans pass with the course certificate in both formats, with only the failures already listed; the demo's guards have 60 mutants of their own, all killed. What M5 cannot do alone: issuing to the EU reference wallets on real phones needs the demo online, and building them here needs a phone toolchain this machine lacks room for; the OIDF certification run is a submission to the Foundation.
