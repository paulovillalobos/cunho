# cunho: security review of the engine, the demo and the live deployment

Reviewed: branch `demo-flow` at `9e96bbf`, which is also what runs at `https://issuer.foaap.app` (`/pid`, `/course`) and `https://demo.foaap.app`, on 11 November 2026, the day the demo went online.
Fixes: branch `security-review`, commits `966d6eb`, `48e9068`, `ada967f`, `25301d3` and `2b374bb`, and, for what the redeploy showed at the edge, branch `edge-error-answers`, commit `abb8670`; each finding with a test that failed before its fix.
Deployed: `c965675`, the head of the first branch, on 12 November 2026 with the owner's yes, and after its merge into `demo-flow` the merge commit `0f1677c`, which differs from it only in this record and in `docs/DEMO.md` (section 8). `abb8670` is not deployed yet.

## 1. Scope

1. **The issuer engine** (`src/cunho/`), read against OpenID4VCI 1.0 and HAIP, RFC 9449 (DPoP), 9126 (PAR), 7636 (PKCE), 9101, 9396, 6749, 6819 and 9700, the Token Status List draft, SD-JWT VC (RFC 9901), ISO/IEC 18013-5, and what eIDAS 2 and the ARF ask of an issuer.
2. **The demo service** (`src/cunho_demo/`) and its page (`static/`), with the tools that build and start the stack (`tools/`, `deploy/`).
3. **The live deployment**: the host, Docker, Caddy, the renewal cron job, and what the two hosts and `foaap.app/vct/*` answer from outside.
4. **The supply chain**: the image, its base images, the Python packages, the CI.

The demo is public on purpose: every route of both hosts is reachable by anyone, and the findings are judged with that in mind. The rest of `foaap.app` is out of scope and was not touched.

## 2. Method

The code was read in six passes, one area each: the OAuth front door (token endpoint, PAR, authorization, DPoP, client authentication); the issuance state machine (offers, grants, deferred issuance, notification, refresh); formats and parsers (JOSE, JWE, CBOR and COSE, SD-JWT VC, mdoc, status lists); trust and everything cunho fetches (certificate paths, CRL and OCSP, the list of wallet providers, wallet providers' status lists, revocation chaining); storage, the audit log and keys; the demo's page, phone page and tooling. A seventh pass read the deployment and the supply chain.

A weakness counted as a finding only once a test reproduced it on the code as reviewed. Those tests are now in the suite, where each holds its fix. Beside reading, the passes ran their own fuzzing against a local instance, never the live one: about 1,400 signed DPoP proofs, 1,300 form and query variants and 8,600 raw header, path and query variants at the front door; 300,000 random inputs to the JSON parser and 200,000 to the CBOR decoder; 13.7 million mutations of COSE and CBOR messages and of status lists; some 6,000 fuzzed sets of subject data; a randomised tamper harness on the audit log; a model of the Caddy rule that keeps the operator API inside, against 2.18 million request targets.

The live deployment was read, not changed: a handful of requests to each host, one TCP connect scan of the server's IPv4 address, and read-only commands on the server. No load test, no fuzzing against it. Two things were confirmed live with one request each (S-01 and E-18 below). The stack was rebuilt locally, in a project of its own, to try every change to it before proposing it.

Severity: **Critical** is a credential bound to a key its holder does not hold, a forged credential, or a way to the keys or to personal data. **High** is a MUST that can be bypassed, an issuer that anyone can take out of service, or revocation that silently stops. **Medium** is a conformance gap or a weakness a national PID provider would block a release on; for the demo, something that takes it away from other visitors. **Low** is hygiene, defence in depth, or a failure only an operator can cause. **Info** is noted for a decision, or needs no change.

## 3. Summary

No Critical finding: no path was found to a credential on a key that was not proven, to a forged credential or status list, to another subject's data, to a signing key, or to the operator API from outside.

The three High findings are in code a production issuer runs and the demo does not: they need the list of wallet providers, wallet providers' status lists or fetched revocation, and the demo's issuers have no route out and fetch nothing. Of the three Medium findings left, one is a design decision (E-21) and two wait for changes on the server (D-02, D-12). "Fixed on the branch" means fixed in the repository; the first branch was deployed on 12 November 2026, and two findings, D-12 and D-13, came out of the deployment itself (section 8). Observations, with no change made: operator tokens have no roles, so the demo service's token can do whatever any operator can; `tx_code_max_attempts` has no ceiling against the PIN's length (10,000 attempts on a four-digit PIN starts); a "revoked" OCSP answer is not kept, so whoever holds a revoked signer's key can still spend the limit of requests to that responder's host (the residue of E-02; an existing test asks for a revoked answer to be asked again); `/notification` does not look at the closed mark; the issuer metadata is rebuilt on every GET and its route has no limiter (about 3 ms a request); the check that a status token is fresh within 24 hours adds up `ttl`, not the token's lifetime (25 hours at the defaults for a verifier that goes by `exp` alone); the mark that closes a subject lives as long as a subject can have credentials issued by the lifetimes as they are set at that moment, so after a restart that shortens them all an access token from before it could outlive the mark (the subject's refresh token and held issuances are removed at the close itself, E-16); opening a new status list lays its decoys inside a wallet's request (45 ms at the default size, about 3 s at the largest); DESIGN section 6 says nobody can swap the wallet's response key in transit, which request encryption without sender authentication gives only against a key being altered, not replaced.

## 7. What is known and expected, with a verdict

- **Development mode.** The demo's issuers trust wallet providers from a PEM file, which production refuses by design. With it they accept the demo wallet's own attestations, signed by a key the demo service holds, so a credential from the demo says nothing about where its key is kept. **Fine for a demo**: its credentials are test data under a development PKI no relying party should trust. A real risk only if someone took the demo's issuer certificates for a real issuer's.
- **A development PKI.** A root made at the first start, certificates of 30 days renewed by a monthly cron job. **Fine for a demo.** The cost is availability: a renewal that fails silently ends issuance within the month (D-10), and the demo wallet needs the demo service restarted after each renewal (S-08).
- **Status lists published every 60 seconds, without jitter.** A visitor who revokes a test credential sees it within a minute. Whoever watches a list sees the bits of one subject's batch change together, which is what the jitter of an hour that production defaults to is there to hide. **Fine for a demo; a real risk in production**, where it would tell a watcher which entries belong to one person.
- **Credentials of 30 days.** Test data on test keys. **Fine for a demo.**
- **`/offers/*` open to anyone.** It serves a credential offer by its reference, as OpenID4VCI's `credential_offer_uri` asks, and `/o/*` the phone page for it. What it exposes is the offer itself: which credential, the issuer, and for the pre-authorized flow the pre-authorized code, never the PIN, which only the page that made the offer is told. Whoever holds the reference can do what whoever scans the QR code can: have that test persona's credential issued to a wallet. The reference is 144 random bits, compared in constant time, on a rate-limited route, and ends with the offer. **Fine for a demo**, and the same as the QR code on the screen.
- **The demo is public, with no password in front of it.** By decision. The findings above are judged for a service anyone can reach.

## 9. What was checked and found sound

**The OAuth front door.** Pre-authorized codes of 256 bits, stored hashed and sealed, taken once and atomically. Wrong transaction codes counted by an atomic increment before a constant-time comparison: 120 wrong codes sent at once over four database connections were compared exactly five times. All twelve DPoP checks; ES256, ES384 and ES512 only; `htu` from the settings, never from the request; the `jti` cache keyed by key and `jti`, added atomically (40 replays at once: one accepted); a stateless nonce. Access tokens of 256 bits, hashed and sealed, no downgrade to Bearer, never in a query. Every stored row sealed with a MAC over its key, its content and its expiry, under a purpose of its own. PAR, authorization and login: the client authenticated first, an exact redirect URI, S256 only, a request URI of 256 bits bound to its client and opened eight times at most, the login state and the completion secret of 256 bits, the latter only in the operator API's answer and stored hashed; redirects only to the login service or to the sealed redirect URI, with `iss` and `state`. The code: 256 bits, 60 seconds at most, taken in the transaction that writes the token, bound to the client, its instance key, the DPoP key, PKCE and the redirect URI. A refresh token bound to the wallet solution and its instance key, which never widens what was authorized. Wallet attestations: one of each header, the path, the signature, `aud`, `exp`, `cnf`, the proof of possession's `aud`, `iat` and `jti`, `client_id` equal to `sub`. HTTP: 256 KiB on every body, strict UTF-8 forms, repeated parameters refused, fixed error text, one limiter table per route group, bounded, with IPv6 by /64; the operator token compared in constant time before a body is read.

**Issuance.** The token authorises all three endpoints; a token asks only for the configurations of its own offer or login; nothing crosses from one offer to another. The closed mark is checked inside the transaction that issues. A configuration and its keys are claimed in one transaction and given back when the request fails. A repeated request gets the first one's answer only under the same token, configuration and keys, with fresh proofs, and that answer is kept sealed. A transaction id of 256 bits, bound to its subject; a decision written with its log entry; notification ids of 144 bits. A response is encrypted only to an encrypted request, with ECDH-ES and on-curve checks. A credential's validity is the least of the configured days, the status periods and the document's end. The vault entry goes when every configuration has been issued.

**Formats and parsers.** Strict JSON: duplicate names, NaN and Infinity, integers over twenty digits, a byte order mark, UTF-16 and UTF-32 and lone surrogates all refused. A compact JWS of exactly three parts under a size cap, `crit` refused, `jku`, `x5u` and `kid` never followed. A JWK's curve bound to its algorithm, coordinates of exact length, on the curve, private members refused. JWE: the token and DPoP checked before anything is decrypted, `zip` and `crit` refused, the ephemeral key on the request key's curve, 12-byte IVs and 16-byte tags, the protected header as associated data, no oracle beyond the tag. CBOR and COSE: depth of 32, indefinite lengths, duplicate keys and trailing bytes refused. SD-JWT VC: salts of 128 bits, fresh for every copy; decoys that cannot be told from digests; protocol claims written after subject data; `cnf` with the public key only. An independent RFC 9901 reading of a batch of thirty found 870 salts all different, thirty status indexes all different, one `nbf` and `exp`. mdoc: salts of 32 bytes, digest ids drawn without repeat, the deterministic encoding, the device key from the proven key. Status indexes from the system's random source, reserved atomically, never reused; published bits only ever set. Signatures from an HSM or a KMS verified before use.

**Proofs and trust.** No algorithm confusion in proofs; the nonce consumed only after every signature check; `aud`, `iat`, `typ` and `iss`; a key attestation's type, times, attested keys, storage and user authentication levels, nonce and status period, and an attestation for one key cannot vouch for another. Path validation: anchors matched also through a rollover, validity, CA flags, keyCertSign, path length, extended key usage, unknown critical extensions, name constraints refused, the policy tree, key sizes, a chain of five at most. OCSP in full; CRLs complete, the newest deciding, with a watermark against replay. Wallet providers' status lists under a 16 MiB inflate cap, the watermark raised only after the signer is trusted. The list of wallet providers accepted only under the pinned signer, with a sequence number that never goes back. Every development-only permission refused in production, with the one gap of E-21. The control flow of revocation chaining: the lease, fenced revocations, each list read once a run, an older check never written over a newer one.

**Storage, the audit log and keys.** The vault's encryption binds the subject reference, so one subject's rows copied under another's reference open nothing. Keyring purposes kept apart; a master secret of at least 32 bytes; secret, PIN and key files refused when others can read them; a PIN never in the environment or on a command line. The audit log: the tamper harness found no change to a covered entry that verification missed; the head, the checkpoint and the anchor under separate MAC purposes; malformed rows fail verification and never raise. **The demo's page.** One `innerHTML`, fed by the QR code library's own SVG; every link built from the configured origin and a server token; everything else written as text. The wallet's name reaches one screen, escaped. No `target=_blank`, no script from elsewhere, local storage holds only the view mode. The PIN is only in the answer to the page that made the offer.
