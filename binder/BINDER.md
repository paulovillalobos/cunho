# The binder: EUDI issuer requirements -> tests

One traceability matrix from every issuer requirement in EU law, the ARF and the protocol specs to the test that proves it. It is the core spec for our Apache-2.0 EUDI credential issuer (each row proposes an `our_rule_id` for the rule registry) and the yardstick for grading public issuers (each blackbox row names the probe check that grades it, or the check we still have to write).

**Inputs** (all in this folder unless noted): `arf-issuer-requirements.md` (ARF 3.0.0 HLRs @f5789a7, TS3 v1.5.2, PID Rulebook v1.7), `eidas-issuer-obligations.md` (147 rows from 910/2014 as amended and the implementing acts up to 2026/1731, 2026/1735), `CHECKLIST.md` (OpenID4VCI 1.0, RFC 9449, HAIP 1.0, Token Status List draft-21, SD-JWT VC draft-23, ISO/IEC 18013-5) and the probe catalogue `~/Downloads/eudi-issuer-pro/probe/eudi_probe/checks.py` (129 checks). Machine-readable copy: `BINDER.csv`.

**M3 rows** (28, added 2026-11-05): the rules the authorization code flow, wallet attestation, trusted lists, signed metadata and refresh tokens need and no row above carried, from FAPI 2.0 (which HAIP §4 pulls in), RFC 9126, 7636, 9207, 9449, 9700, 8414, 5280 and 6960, draft-ietf-oauth-attestation-based-client-auth-07, OpenID4VCI 1.0, ETSI TS 119 602, ARF 3.0.0 and TS3. Each gives its own layer and source, and its strength and quote are in `BINDER-STRENGTH.csv`.

**M4 rows** (2, added 2026-11-09): encrypted credential requests and responses, from OpenID4VCI 1.0 §8.2, §8.3, §9, §10 and §12.2.4, with their strengths and quotes in `BINDER-STRENGTH.csv`.

**How to read a row**

- `layer`: law (eIDAS + implementing acts), arf (ARF HLR), ts (TS3; ETSI TS for the M3 rows), rulebook (PID Rulebook), spec (protocol items from CHECKLIST.md that no ARF/eIDAS row carries, and most M3 rows).
- `testability`: **blackbox** = gradable from outside over HTTP against any issuer (the probe); **fixture** = needs a controlled environment the public issuer will not give us (a Wallet Provider CA the issuer trusts, a revocable WIA/KA, a rulebook schema, an opt-out user); **unit** = internal behaviour we prove with unit/integration tests in our own code; **organisational** = policy, registration or notification duty.
- `probe_checks` + `new_check_needed` on the same row = the probe covers part, the new check closes the rest.
- Deduplication: where an ARF/TS/rulebook row and a law row require the same thing, both rows stay (different layers), the narrower one points to the other in `depends_on`, and both carry the same `our_rule_id`. A few rows carry two rule ids separated by `;` because the source text bundles two checks.
- Wallet-side ARF HLRs (arf-issuer-requirements.md §11) are included as `binds = Wallet` rows because the issuer's output must pass them; their text is paraphrased in the input, so those rows group the IDs exactly as the input does.
- Not included: HLRs marked Empty in ARF 3.0.0 (ISSU_04, ISSU_16, ISSU_18a, ISSU_22a/b, ISSU_31, ISSU_32a, ISSU_66, PID_15, WUA_13-16, WUA_18-21, WUA_23) and the ISSU_67/69/72 cross-reference line in ARF §8 (already rows).
